# ५ — अक्षरको गुफा: srcML र XPath

पाँचौं टापुमा एउटा गुफा छ। गुफाको भित्तामा कसैले पुरानो कोड कुँदेको छ, र हरेक लाइनको वरिपरि साना साना कोष्ठक जस्ता चिन्ह कोरिएका छन्।

रोबिनले मसाल उठाइन्, र भित्ता नजिकबाट हेरिन्। [robin]"यहाँ कोड मेटिएको छैन,"[/] उनले भनिन्। [robin]"कसैले कोडको एउटा अक्षर पनि फेरेको छैन। केवल वरिपरि नाम लेखेको छ, ताकि कुन टुक्रा function हो र कुन टुक्रा call हो भनेर चिनियोस्।"[/]

यही srcML को विचार हो। srcML ले source code लाई XML मा बदल्छ। तर त्यसले code को अक्षर फ्याँक्दैन। हरेक अक्षर, हरेक खाली ठाउँ, र हरेक comment जस्ताको तस्तै रहन्छ, र बीचमा XML का tag मात्र थपिन्छन्।

यसको अर्थ के हो? XML बाट tag हटायौ भने ठीक उही source फिर्ता आउँछ, byte byte उस्तै। यसलाई round trip भनिन्छ, र Python को ast ले यो गर्न सक्दैनथ्यो।

srcML ले C, C++, C sharp, र Java बुझ्छ। अर्को खास कुरा के हो भने, यसलाई code compile हुनु पर्दैन। header file नभए पनि, macro नखुले पनि, आधा लेखिएको code भए पनि यसले रुख बनाउँछ। यसैले पुराना ठूला codebase को research मा srcML धेरै प्रयोग हुन्छ।

@read teach
अब tag का नाम सुन। सबैभन्दा बाहिर unit हुन्छ, र एउटा file एउटा unit हो। त्यसभित्र function, class, decl_stmt, if, while, call, र expr जस्ता tag हुन्छन्। हरेक function भित्र name, parameter_list, र block हुन्छन्।

यी सबै tag एउटा namespace मा हुन्छन्, र त्यसको छोटो नाम src हो। त्यसैले खोज्दा function होइन, src colon function लेखिन्छ।

खोज्ने भाषा XPath हो। XPath मा दुई वटा slash को अर्थ कहीं पनि भित्र भन्ने हुन्छ। एउटा slash को अर्थ सिधै भित्र भन्ने हुन्छ। ठूलो कोष्ठक भित्र शर्त लेखिन्छ, र त्यसलाई predicate भनिन्छ।

अब यो गुफामा खोज्ने तरिका एकैचोटि सुन।

@algo srcml-xpath
srcML मा code खोज्ने तरिका यस्तो छ। पहिलो, srcml command लाई source file देऊ, र त्यसले XML file बनाउँछ, जसमा भाषा file को extension बाट थाहा हुन्छ। दोस्रो, खोज्नु पर्ने कुराको tag सोच, जस्तै function, call, वा decl_stmt, र हरेक tag अगाडि src colon लगाऊ। तेस्रो, XPath लेख। दुई slash src colon function ले सबै function दिन्छ। त्यसमा ठूलो कोष्ठक भित्र src colon name बराबर main राख्यो भने main नामको function मात्र आउँछ। त्यसपछि दुई slash src colon call थप्यो भने त्यो function भित्रका सबै call आउँछन्। चौथो, त्यो XPath srcml को xpath option मा, वा lxml जस्तो library मा src namespace दिएर चलाऊ। पाँचौं, नतिजा बदल्नु छ भने XML मै बदल, र srcml लाई त्यही XML फिर्ता देऊ, र source बन्छ, जहाँ तिमीले नछोएको हरेक अक्षर पहिलेकै जस्तो रहन्छ।
@end

रोबिनले मसाल अर्को भित्तातिर सारिन्। [robin]"एउटा उदाहरण सुन,"[/] उनले भनिन्। [robin]"हामीलाई कुन कुन function ले malloc बोलाउँछन् भनेर थाहा पाउनु छ।"[/]

त्यसको XPath यस्तो हुन्छ। दुई slash src colon function, अनि ठूलो कोष्ठक भित्र दुई slash src colon call slash src colon name बराबर malloc, अनि बाहिर slash src colon name लेखिन्छ। अर्थात्, malloc को call भएका function खोज, र तिनको नाम देऊ।

उसप्पले आँखा चिम्ल्याएर सोच्यो। [usopp]"त्यो त अङ्ग्रेजीको वाक्य जस्तै रहेछ,"[/] उसले भन्यो।

[robin]"हो,"[/] रोबिनले भनिन्। [robin]"XPath ले रुखमा बाटो भन्छ। कहाँबाट सुरु गर्ने, कुन हाँगा समात्ने, र कुन शर्तमा रोकिने भन्ने कुरा एउटै लाइनमा आउँछ।"[/]

XPath मा count जस्ता function पनि छन्। count भित्र दुई slash src colon if राख्यो भने, file मा कति वटा if छन् भनेर आउँछ। यसैले सरल नाप लिने काम एउटा लाइनमै हुन्छ।

@recall srcml-xpath | गुफाको भित्तामा मसालको उज्यालो नाच्छ, र हामी खोज्ने तरिका फेरि सुन्छौं।

@read hush
गुफाको छानाबाट एक थोपा पानी झर्‍यो। त्यो आवाज भित्रसम्म गुन्जियो, अनि शान्त भयो।

अब srcML का सीमा पनि सुन। srcML ले type जान्दैन। x को type के हो भनेर सोध्यौ भने, decl_stmt बाट नाम र type को text मात्र भेटिन्छ, तर त्यसको पूरा अर्थ भेटिँदैन। Java को method call कुन class को method हो भन्ने कुरा पनि srcML ले resolve गर्दैन।

त्यसैले srcML धेरै file मा छिटो ढाँचा खोज्न, code लाई ठूलो मात्रामा नाप्न, र formatting नबिगारी सरल बदलाव गर्न उपयुक्त हुन्छ। गहिरो अर्थ चाहियो भने अर्को औजार चाहिन्छ।

@recall srcml-xpath | गुफा छोड्नुअघि यो तरिका अन्तिम पटक सुन।

@read hush
रोबिनले मसाल निभाइन्। भित्ताका अक्षर अँध्यारोमा हराए, तर ती त्यहीँ छन्, जस्ताको तस्तै।

@tier medium

अब बदल्ने कामको कुरा अलि विस्तारमा सुन। srcML सँग XSLT प्रयोग गर्न सकिन्छ। XSLT भनेको XML लाई अर्को XML मा बदल्ने भाषा हो। जस्तै, हरेक function को block को सुरुमा एउटा log को statement थप्ने नियम XSLT मा लेखिन्छ।

तर धेरैजसो मान्छे XSLT भन्दा Python र lxml रोज्छन्। lxml ले XML पढ्छ, XPath चलाउँछ, र node थप्न वा हटाउन दिन्छ। अन्त्यमा XML लेखेर srcml लाई फिर्ता दिइन्छ।

यहाँ एउटा सावधानी छ। नयाँ code थप्दा त्यो पनि srcML को रूपमा थप्नुपर्छ, वा कम्तीमा text को रूपमा सही ठाउँमा राख्नुपर्छ। tag गलत ठाउँमा राख्दा पनि source फर्किन्छ, तर अर्को पटक खोज्दा रुख अनौठो देखिन्छ।

srcML ले पूरै project पनि एउटै archive मा राख्न सक्छ। हरेक file एउटा unit बन्छ, र सबै unit एउटै बाहिरी unit भित्र हुन्छन्। त्यसपछि एउटै XPath ले हजारौं file एकैचोटि खोज्छ।

@tier long

ब्रुक गुफाको मुखमा बसेर सुनिरहेको थियो। [brook]"यो गुफा मलाई पुरानो संगीतको किताब जस्तो लाग्यो,"[/] उसले भन्यो। [brook]"सुर फेरिँदैन, केवल किनारमा कसैले नाम लेखिदिएको हुन्छ।"[/]

यो उपमा ठीक छ। AST ले गीतको आकार मात्र राख्छ, र सुर आफैं बनाउँछ। srcML ले सुर पूरै राख्छ, र आकार किनारमा लेख्छ।

अब तीन वटा रुखका जङ्गल एकैचोटि सम्झौं। Python को ast ले Python को रुख दिन्छ, र अर्थ मेटिँदैन तर comment हराउँछ। Java का औजारले type सहितको रुख दिन्छन्, तर compile हुने setup चाहिन्छ। srcML ले धेरै भाषामा अक्षर नबिगारी रुख दिन्छ, तर type दिँदैन।

interview मा यस्तो प्रश्न आउन सक्छ कि दस लाख लाइनको पुरानो C++ codebase मा कति function ले exception फाल्छन्। त्यसको राम्रो उत्तर srcML र XPath हो, किनभने त्यो code compile गराउनै गाह्रो हुन सक्छ, र srcML लाई compile चाहिँदैन।

@read hush
गुफा पछाडि छुट्यो। बाहिर हावा अलि चिसो छ, तर जहाजको कम्बल न्यानो छ। तिमी त्यही कम्बलमा बेरिएर सुनिरहेका छौ।
