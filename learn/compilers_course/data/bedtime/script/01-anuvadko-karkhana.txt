# १ — अनुवादकको कारखाना: compiler pipeline

पहिलो टापुमा एउटा ठूलो कारखाना छ। त्यसको छानाबाट सेतो धुवाँ बिस्तारै उठ्छ, र भित्रबाट गियर घुमेको मधुरो आवाज आउँछ।

फ्राङ्की सबैभन्दा पहिले जहाजबाट ओर्लियो। [franky]"यो त मेरो खालको ठाउँ रहेछ,"[/] उसले भन्यो। [franky]"यहाँ एउटा लामो belt छ, र belt माथि सामान एक कोठाबाट अर्को कोठामा जान्छ।"[/]

कारखानाको ढोकामा एउटा कागज झुण्डिएको छ। त्यसमा मान्छेको भाषामा लेखिएको एउटा वाक्य छ, र त्यो वाक्य यस्तो छ — [aside]"x बराबर a प्लस b गुणा c हुन्छ।"[/]

कारखानाको अर्को छेउमा मेसिन पर्खिरहेको छ। मेसिनले यो वाक्य बुझ्दैन। मेसिनले केवल सानो सानो आदेश बुझ्छ, जस्तै यो register मा यो मान राख, र ती दुई मान जोड।

बीचको यो सारा बाटोलाई compiler pipeline भनिन्छ। र यो बाटोमा हरेक कोठाले एउटा मात्र काम गर्छ।

@read teach
पहिलो कोठामा lexer बस्छ। lexer ले अक्षरको लामो लाइन पढ्छ, र त्यसलाई शब्दमा टुक्र्याउँछ। ती शब्दलाई token भनिन्छ। x एउटा token हो, बराबरको चिन्ह अर्को token हो, a अर्को token हो।

दोस्रो कोठामा parser बस्छ। parser ले token को लाइन लिन्छ, र त्यसबाट रुख बनाउँछ। त्यो रुखलाई AST भनिन्छ, र यसको पूरा नाम abstract syntax tree हो।

रुखमा के देखिन्छ? माथि assignment छ। त्यसको बायाँ x छ। दायाँ प्लसको गाँठो छ। प्लसको एकातिर a छ, र अर्कोतिर गुणाको गाँठो छ, जसमुनि b र c छन्। गुणा तल छ, किनभने गुणा पहिले हुन्छ।

तेस्रो कोठामा semantic analysis हुन्छ। यहाँ नामहरू खोजिन्छन्। a भनेको कुन variable हो, त्यो कहाँ घोषणा भएको छ, र त्यसको type के हो भन्ने कुरा यहाँ जाँचिन्छ। यस कामलाई name resolution र type checking भनिन्छ।

चौथो कोठामा रुखलाई सिधा लाइनमा झारिन्छ। यस कामलाई lowering भनिन्छ, र यसले IR बनाउँछ। IR भनेको intermediate representation हो, र यो मान्छे र मेसिनको बीचको भाषा हो।

पाँचौं कोठामा optimization हुन्छ। यहाँ IR लाई छोटो र छिटो बनाइन्छ, तर त्यसको अर्थ फेरिँदैन। अन्तिम कोठामा code generation हुन्छ, र त्यहाँ IR बाट machine code बन्छ।

अब यो सारा बाटो एकैचोटि सुन। यो आजको पहिलो तरिका हो।

@algo pipeline
compiler pipeline का चरण यी हुन्। पहिलो, lexer ले source code का अक्षर पढेर token को लाइन बनाउँछ, र whitespace र comment फ्याँक्छ। दोस्रो, parser ले grammar अनुसार token मिलाएर AST बनाउँछ। तेस्रो, semantic analysis ले symbol table बनाउँछ, हरेक नामलाई त्यसको घोषणासँग जोड्छ, र type जाँच्छ। चौथो, lowering ले AST लाई three-address code जस्तो IR मा झार्छ, र त्यसलाई basic block र CFG मा बाँड्छ। पाँचौं, optimizer ले IR मा analysis चलाएर अर्थ नफेरिने गरी कोड सुधार्छ। छैटौं, backend ले register छान्छ, instruction छान्छ, र machine code लेख्छ। पहिलेका तीन चरणलाई frontend भनिन्छ, बीचको भागलाई middle end भनिन्छ, र अन्तिम भागलाई backend भनिन्छ।
@end

फ्राङ्कीले belt को छेउमा हात राख्यो। [franky]"यो विभाजनको खास फाइदा सुन,"[/] उसले भन्यो। [franky]"धेरै भाषाका frontend र धेरै मेसिनका backend छन् भने, बीचमा एउटै IR राख्दा सबै जोडिन्छन्।"[/]

यो कुरा LLVM ले देखाएको हो। C, Rust, Swift जस्ता भाषाका frontend ले LLVM IR बनाउँछन्। अनि त्यही IR बाट x86 र ARM दुवैका लागि machine code बन्छ। दस भाषा र पाँच मेसिन भए पचास compiler चाहिँदैन। दस frontend र पाँच backend भए पुग्छ।

नामीले नक्सामा एउटा रेखा कोरिन्। [nami]"हाम्रो यात्राका लागि यो कुरा झन् महत्त्वपूर्ण छ,"[/] उनले भनिन्। [nami]"हामी machine code बनाउन आएका होइनौं। हामी कोड बुझ्न आएका हौं। त्यसैले हाम्रो काम प्रायः बीचका कोठामा हुन्छ।"[/]

यो साँचो हो। static analyzer ले पनि compiler कै आधा बाटो हिँड्छ। त्यसले lexer र parser चलाउँछ, AST बनाउँछ, कहिलेकाहीँ IR र CFG बनाउँछ, अनि त्यहाँ रोकिन्छ। machine code लेख्नुको सट्टा त्यसले report लेख्छ।

@recall pipeline | अब belt फेरि बिस्तारै घुम्छ, र हामी त्यही चरणहरू फेरि सुन्छौं।

@read hush
कारखानाको गियर उही लयमा घुमिरहेको छ। धुवाँ आकाशमा बिलाउँदै छ।

अब एउटा सानो प्रश्न सोध, र त्यो interview मा प्रायः आउँछ। interpreter र compiler मा के फरक छ?

compiler ले पूरै program पहिले नै अर्को भाषामा बदल्छ, र त्यसपछि त्यो चलाइन्छ। interpreter ले program लाई एक एक गरी पढ्दै तुरुन्तै चलाउँछ। तर आजका धेरै भाषा बीचमा छन्। Python ले पहिले bytecode बनाउँछ, अनि त्यो bytecode लाई एउटा virtual machine ले चलाउँछ। Java ले पनि bytecode बनाउँछ, र JVM ले तातो भागलाई JIT गरेर machine code बनाउँछ।

त्यसैले असल उत्तर यस्तो हुन्छ — भाषा आफैं compiled वा interpreted हुँदैन, उसको implementation हुन्छ।

@recall pipeline | टापु छोड्नुअघि यो belt को गीत अन्तिम पटक सुन।

@read hush
फ्राङ्कीले कारखानाको ढोका बिस्तारै बन्द गर्‍यो। हामी फेरि जहाजतिर फर्कियौं।

@tier medium

अब पाँचौं कोठा, optimizer, लाई अलि नजिकबाट हेरौं।

optimizer ले के गर्छ भन्ने कुराका केही साधारण उदाहरण छन्। पहिलो constant folding हो। कोडमा दुई गुणा तीन लेखिएको छ भने compiler ले चलाउनुअघि नै त्यसलाई छ बनाउँछ।

दोस्रो dead code elimination हो। कुनै variable मा मान राखियो तर त्यो कहिल्यै पढिएन भने, त्यो काम हटाइन्छ। तेस्रो common subexpression elimination हो। उही हिसाब दुई ठाउँमा छ भने, एकपटक मात्र गरिन्छ।

यी सबै सुधारको पछाडि एउटै प्रश्न हुन्छ। यो सुधार गर्दा program को अर्थ फेरिन्छ कि फेरिँदैन? त्यो प्रश्नको उत्तर दिन compiler ले analysis चलाउँछ। यसैले analysis र optimization सधैं सँगै हिँड्छन्।

यहीँ हाम्रो यात्राको गाँठो देखिन्छ। जुन dataflow analysis ले compiler लाई dead code चिनाउँछ, त्यही analysis ले bug खोज्ने औजारलाई पनि बाटो देखाउँछ। औजार एउटै हो, तर काम दुई वटा हुन्छन्।

@tier long

चपर belt को छेउमा उभिएर हेरिरहेको थियो। [chopper]"तर lexer र parser किन छुट्टै कोठामा छन्?"[/] उसले सोध्यो। [chopper]"एउटै कोठाले दुवै काम गर्न सक्दैन?"[/]

[franky]"सक्छ,"[/] फ्राङ्कीले भन्यो। [franky]"तर छुट्याउँदा दुवै सजिलो हुन्छन्। lexer ले अक्षरको झन्झट सम्हाल्छ। parser ले केवल संरचना सोच्छ।"[/]

त्यो विभाजनको अर्को फाइदा पनि छ। lexer लाई regular expression जस्तो सरल नियमले बनाउन सकिन्छ, र त्यो एकदमै छिटो हुन्छ। parser लाई grammar चाहिन्छ, किनभने कोष्ठक भित्र कोष्ठक जस्ता कुरा regular expression ले गन्न सक्दैन।

अर्को रोचक कुरा यो हो कि AST मा सबै कुरा हुँदैन। कोष्ठक, अल्पविराम, र अर्धविराम जस्ता चिन्ह रुखको आकारले नै भनिदिन्छ, त्यसैले ती रुखमा राखिँदैनन्। यसैले यसलाई abstract भनिन्छ। सबै चिन्ह राख्ने रुखलाई concrete syntax tree वा parse tree भनिन्छ।

यो फरक हाम्रो यात्रामा फेरि आउँछ। कोड बदलेर फेरि लेख्नुपर्दा comment र खाली ठाउँ हराउन सक्छन्, किनभने AST ले ती सम्झँदैन। srcML र tree-sitter जस्ता औजारले यही समस्या समाधान गर्छन्।

@read hush
जहाजको डेकमा अब हावा शान्त छ। कारखानाको धुवाँ टाढा पुगिसक्यो। तिमी सुनिरहेका छौ, र belt को आवाज बिस्तारै समुद्रको आवाजमा मिसिँदैछ।
