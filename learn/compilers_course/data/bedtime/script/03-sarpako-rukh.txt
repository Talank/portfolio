# ३ — सर्पको जङ्गल: Python को ast module

तेस्रो टापुमा एउटा घना जङ्गल छ। यहाँका रुखका हाँगामा लामा हरिया सर्प बेरिएका छन्, तर तिनीहरू डसेनन्। तिनीहरू शान्त छन्, र बिस्तारै सास फेरिरहेका छन्।

रोबिन एउटा ठूलो रुखको फेदमा रोकिइन्। [robin]"यो जङ्गल Python को हो,"[/] उनले भनिन्। [robin]"यहाँ हरेक Python file एउटा रुख बन्छ, र त्यो रुख हेर्ने औजार Python भित्रै आउँछ। त्यसको नाम ast module हो।"[/]

पहिलो काम रुख उमार्नु हो। ast dot parse लाई source code को string दिइन्छ, र त्यसले Module नामको जरा फिर्ता दिन्छ। Module भित्र body नामको सूची हुन्छ, र त्यो सूचीमा file का हरेक statement हुन्छन्।

हरेक node एउटा class को object हो। FunctionDef, Assign, Call, Name, र Constant यस्ता class हुन्। हरेक node सँग _fields नामको सूची हुन्छ, र त्यसले कुन कुन child छन् भनेर भन्छ। हरेक node सँग lineno र col_offset पनि हुन्छन्, र तिनले source मा त्यो node कहाँ छ भनेर देखाउँछन्।

रुखको आकार हेर्न ast dot dump प्रयोग गरिन्छ। त्यसले रुखलाई लामो text मा छाप्छ। सुरुमा अलि डरलाग्दो लाग्छ, तर दुई तीन पटक हेरेपछि आँखाले आकार चिन्न थाल्छ।

चपर एउटा सर्पको नजिक गयो। [chopper]"अब यो रुखका सबै हाँगा कसरी घुम्ने?"[/] उसले सोध्यो।

@read teach
त्यसका लागि NodeVisitor छ। तिमी NodeVisitor को subclass बनाउँछौ, र जुन किसिमको node मा रुचि छ, त्यसका लागि visit underscore पछि class को नाम भएको method लेख्छौ। जस्तै, function call मा रुचि छ भने visit_Call लेख्छौ।

अब त्यो घुम्ने तरिका ठीक ठीक सुन। यो आजको तरिका हो, र interview मा यसलाई यसरी नै भन्न सकिन्छ।

@algo node-visitor
NodeVisitor ले रुख यसरी घुम्छ। पहिलो, तिमीले visit मा कुनै node दियौ भने, त्यसले त्यो node को class को नाम हेर्छ, र visit underscore सँग त्यो नाम जोडेर method को नाम बनाउँछ। दोस्रो, त्यो नामको method तिम्रो class मा छ भने त्यही बोलाउँछ, र छैन भने generic_visit बोलाउँछ। तेस्रो, generic_visit ले node का हरेक field क्रमैसँग हेर्छ। field को मान सूची हो भने त्यसका हरेक AST node मा visit बोलाउँछ, र मान एउटै AST node हो भने त्यसैमा visit बोलाउँछ। चौथो, यसरी रुख माथिबाट तल, बायाँबाट दायाँ, depth first घुमिन्छ। पाँचौं, तिमीले visit_Call जस्तो आफ्नै method लेख्यौ भने, त्यो node का child आफैं घुमिँदैनन्, त्यसैले भित्रका call पनि चाहिन्छन् भने method को अन्त्यमा self dot generic_visit बोलाउनै पर्छ।
@end

चपरले टाउको कन्यायो। [chopper]"त्यो पाँचौं कुरा मैले पक्कै बिर्सन्थें,"[/] उसले भन्यो।

[robin]"सबैले बिर्सन्छन्,"[/] रोबिनले भनिन्। [robin]"print भित्र अर्को function call छ भने, generic_visit नबोलाउँदा भित्रको call कहिल्यै देखिँदैन। यो Python ast को सबैभन्दा सामान्य bug हो।"[/]

एउटा सानो उदाहरण सुन। तिमीलाई file भित्र eval कति ठाउँमा बोलाइएको छ भनेर खोज्नु छ। visit_Call लेख। त्यहाँ node dot func हेर। त्यो Name हो र त्यसको id eval हो भने, node dot lineno टिप। अनि अन्त्यमा generic_visit बोलाऊ। यति भयो भने सानो security checker तयार हुन्छ।

अर्को सजिलो बाटो पनि छ। ast dot walk ले रुखका सबै node एक एक गरी दिन्छ। तर त्यसले क्रम र प्रसङ्ग दिँदैन। कुन function भित्र छौं भनेर सम्झनु छ भने NodeVisitor नै राम्रो हुन्छ, किनभने visit_FunctionDef भित्र अहिलेको function को नाम राखेर generic_visit बोलाउन सकिन्छ।

@recall node-visitor | सर्पहरू हाँगामा बिस्तारै सर्छन्, र हामी त्यो घुम्ने तरिका फेरि सुन्छौं।

@read hush
जङ्गलमा पात हल्लिन्छन्। कहीं टाढाबाट पानी झरेको आवाज आउँछ।

अब रुखलाई बदल्ने कुरा सुन। त्यसका लागि NodeTransformer छ। यो पनि NodeVisitor जस्तै घुम्छ, तर यहाँ visit method ले जे फिर्ता दिन्छ, त्यसले पुरानो node को ठाउँ लिन्छ।

त्यसका तीन नियम छन्। node नै फिर्ता दियौ भने केही फेरिँदैन। नयाँ node फिर्ता दियौ भने पुरानो साटिन्छ। None फिर्ता दियौ भने त्यो node रुखबाट हटाइन्छ। statement को ठाउँमा सूची फिर्ता दियौ भने, त्यो सूचीका सबै statement त्यहीँ घुसाइन्छन्।

नयाँ node बनाउँदा तिनमा lineno हुँदैन। त्यसैले रुख बदलेपछि ast dot fix_missing_locations बोलाइन्छ, र त्यसले हराएका ठाउँ भरिदिन्छ। अनि ast dot unparse ले रुखलाई फेरि Python code मा लेख्छ, वा compile ले सिधै चलाउन मिल्ने code बनाउँछ।

@recall node-visitor | जङ्गल छोड्नुअघि यो तरिका अन्तिम पटक सुन।

@read hush
रोबिनले रुखको फेदमा हात राखिन्। सर्पहरू निदाए जस्तै शान्त भए। हामी बिस्तारै जहाजतिर फर्कियौं।

@tier medium

अब unparse को एउटा सीमा सुन। ast ले comment सम्झँदैन, र खाली लाइन पनि सम्झँदैन। त्यसैले parse गरेर फेरि unparse गर्दा code चल्छ, तर त्यसको रूप फेरिन्छ।

कोडलाई जस्ताको तस्तै राखेर सानो भाग मात्र बदल्नु छ भने अर्को बाटो चाहिन्छ। LibCST यस्तो औजार हो। यसले concrete syntax tree राख्छ, जसमा खाली ठाउँ र comment पनि हुन्छन्। ठूला codebase मा स्वचालित सुधार गर्दा यही प्रयोग गरिन्छ।

अर्को कुरा, ast ले नाम मात्र देख्छ, अर्थ देख्दैन। x भन्ने Name node ले त्यो x कुन scope को हो भनेर भन्दैन। त्यसका लागि symtable module छ, वा तिमी आफैं visit_FunctionDef र visit_ClassDef मा scope को stack राख्छौ।

Python मा type पनि ast मा हुँदैन। a प्लस b मा a number हो कि string हो, त्यो parse ले भन्दैन। त्यसैले type जाँच्न mypy र Pyright जस्ता औजारले ast माथि आफ्नै ठूलो analysis बनाउँछन्, र ती हामी चौधौं टापुमा भेट्नेछौं।

@tier long

ब्रुकले भायोलिनको तार मिलाउँदै भन्यो — [brook]"मैले एउटा कुरा सुनेको छु। Python ले आफैं पनि यही रुख प्रयोग गर्छ रे।"[/]

यो साँचो हो। Python ले source पढ्दा पहिले token बनाउँछ, अनि PEG parser ले यही AST बनाउँछ। त्यसपछि compiler ले AST लाई bytecode मा बदल्छ। तिमीले ast dot parse बोलाउँदा, Python ले आफ्नै pipeline को बीचको नतिजा तिमीलाई देखाइदिन्छ।

त्यो bytecode हेर्न dis module छ। dis dot dis लाई function दिइयो भने, त्यसले LOAD_FAST र BINARY_OP जस्ता आदेश देखाउँछ। यो stack machine को भाषा हो, र यसले तिमीलाई AST र machine बीचको एउटा तह देखाउँछ।

pytest पनि यही रुखसँग खेल्छ। तिमीले assert a बराबर b लेख्यौ भने, pytest ले import हुनुअघि नै त्यो assert लाई NodeTransformer जस्तो तरिकाले बदल्छ। त्यसैले test असफल हुँदा a र b दुवैको मान सुन्दर रूपमा देखिन्छ।

यसको अर्थ के हो भने, AST बदल्ने काम केवल खेलौना होइन। हरेक दिन लाखौं test चलाउने औजारले यही काम गरिरहेको छ।

@read hush
जङ्गलको हरियो अब अँध्यारोमा मिसियो। पातको सुसाइ बिस्तारै छालको सुसाइ बन्यो। तिमी अझै सुनिरहेका छौ, र त्यो पनि बिस्तारै।
