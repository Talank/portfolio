# १३ — ठूलो बन्दरगाह: Solvers in Practice, LLM र Interview

तेह्रौं टापु यात्राको सबैभन्दा ठूलो बन्दरगाह हो। यहाँ सयौं जहाज आउँछन् र जान्छन्, र किनारमा बत्तीका लहर बलिरहेका छन्।

@read hush
रात भए पनि बन्दरगाह जागै छ। तर यहाँको आवाज शान्त छ, जस्तो धेरै टाढाबाट आएको गीत हुन्छ।

नामीले नक्सा पट्याइन् र भनिन् — [nami]"यो टापुमा हामीले अघिल्ला सबै टापुका औजार साँच्चैको काममा चलेको देख्छौं।"[/]

बन्दरगाहको ढोकामा एउटा ठूलो भवन छ। त्यहाँ हरेक जहाजको सामान जाँचिन्छ। रोबिनले त्यतै औंल्याइन् र भनिन् — [robin]"त्यो भवनमा आजको पहिलो कथा छ।"[/]

@read teach
ठूला cloud कम्पनीमा हजारौं मान्छेले पहुँचका नियम लेख्छन्। AWS मा ती नियमलाई IAM policy भनिन्छ। Zelkova नामको औजारले ती policy लाई SMT सूत्रमा बदल्छ, र सोध्छ कि कुनै अपरिचित मान्छेले यो bucket पढ्न सक्छ कि सक्दैन।

solver ले unsat भन्यो भने कोही पनि पढ्न सक्दैन भन्ने proof हुन्छ। sat भन्यो भने solver ले पढ्न सक्ने ठोस request देखाउँछ। Tiros नामको अर्को औजारले network का बाटा यसरी नै जाँच्छ।

[franky]"अनि अरू कम्पनी?"[/] फ्र्याङ्कीले सोध्यो।

[nami]"Microsoft मा SAGE नामको औजार थियो।"[/] नामीले भनिन्। [nami]"त्यसले symbolic execution र solver मिलाएर Windows का file parser हरूमा लाखौं input बनायो, र धेरै security bug भेट्यो। SLAM नामको अर्को औजारले device driver हरूमा model checking गर्‍यो।"[/]

Intel को कथा पनि छ। processor मा भाग गर्दा गलत उत्तर आउने FDIV bug देखिएपछि, त्यहाँ नयाँ chip को arithmetic formal methods ले जाँच्न थालियो।

@read hush
जाँच गर्ने भवनको बत्ती सधैं बलिरहन्छ। त्यहाँको जाँचकर्ता कसैको मीठो बोलीमा पत्याउँदैन, र सामान आफैं खोलेर हेर्छ।

अब नयाँ युगको कथा आउँछ। बन्दरगाहमा एउटा छिटो बोल्ने व्यापारी आएको छ। उसले एकैछिनमा सयौं कुरा प्रस्ताव गर्छ। त्यो व्यापारी LLM हो।

[usopp]"त्यो व्यापारीले सत्य बोल्छ कि झूट?"[/] उसोपले सोध्यो।

[robin]"कहिलेकाहीँ सत्य बोल्छ, कहिलेकाहीँ झूट बोल्छ, र दुवै बेला उत्तिकै आत्मविश्वासले बोल्छ।"[/] रोबिनले भनिन्। [robin]"त्यसैले उसको सामान जाँचकर्ताको भवनबाट पार हुनुपर्छ।"[/]

@algo llm-loop
LLM र formal methods मिलाउने loop यस्तो छ। पहिलो पाइलामा LLM ले एउटा candidate प्रस्ताव गर्छ, र त्यो proof, loop invariant, specification, वा code हुन सक्छ। दोस्रो पाइलामा भरोसायोग्य checker ले त्यो candidate जाँच्छ, र त्यो checker Lean को kernel, वा Dafny र Z3 हुन सक्छ। तेस्रो पाइलामा जाँच असफल भयो भने checker को ठ्याक्कै error message LLM लाई फिर्ता दे, र फेरि प्रयास गर्न लगाऊ। यो loop एउटा तोकिएको budget सम्म मात्र दोहोर्‍याऊ। चौथो पाइलामा checker ले स्वीकार गरेको कुरा मात्र स्वीकार गर, किनभने भरोसा LLM बाट होइन, checker बाट आउँछ। अन्तमा सम्झ कि specification आफैं गलत हुन सक्छ, त्यसैले specification मान्छेले पढेर जाँच्नुपर्छ।
@end

[zoro]"त्यसो भए व्यापारी किन चाहियो?"[/] जोरोले सोध्यो। [zoro]"जाँचकर्ता मात्र भए पुग्दैन?"[/]

[nami]"जाँचकर्ताले सामान बनाउँदैन।"[/] नामीले भनिन्। [nami]"invariant वा proof खोज्नु गाह्रो काम हो, र जाँच्नु सजिलो काम हो। LLM ले खोज्ने गाह्रो काम छिटो गर्छ। checker ले जाँच्ने काम पक्का गर्छ। दुवै मिलेपछि छिटो र पक्का दुवै हुन्छ।"[/]

यही विचारले AlphaProof जस्ता system बनेका छन्। त्यसले गणित ओलम्पियाडका प्रश्नमा Lean को proof खोज्यो, र Lean ले हरेक proof जाँच्यो। अरू धेरै LLM-guided prover पनि Lean मा tactic सुझाउँछन्, र Lean ले प्रत्येक पाइला स्वीकार गर्छ वा फर्काउँछ।

@read hush
व्यापारीको बोली छिटो छ, तर जाँचकर्ताको कलम बिस्तारै चल्छ। बन्दरगाहको भरोसा त्यही बिस्तारै चल्ने कलममा छ।

@recall llm-loop | यो loop आजको युगको सबैभन्दा चर्चित विचार हो, त्यसैले म यसलाई फेरि एकपटक भन्छु।

अब बन्दरगाहको अर्को छेउमा एउटा सानो कोठा छ। त्यहाँ नयाँ नाविकहरूको परीक्षा लिइन्छ, र त्यो परीक्षा interview जस्तै हुन्छ।

[chopper]"मलाई त डर लाग्यो।"[/] चोपरले भन्यो।

[sanji:gentle]"डराउनु पर्दैन।"[/] सान्जीले भन्यो। [sanji]"प्रश्न जस्तोसुकै आए पनि उत्तर दिने आकार एउटै हुन्छ। राम्रो भान्छेले जुनसुकै परिकार पनि उही क्रममा तयार गर्छ।"[/]

@algo interview
formal methods को interview प्रश्नको उत्तर पाँच पाइलामा दे। पहिलो पाइलामा property लाई ठ्याक्कै फेरि भन, र के सत्य हुनुपर्छ भन्ने स्पष्ट गर। दोस्रो पाइलामा प्रश्न हेरेर औजार छान, र constraint का प्रश्नमा SAT वा SMT छान, सीमित पाइलाभित्रका bug का लागि BMC छान, input बनाउन symbolic execution छान, र पूरा proof का लागि Dafny वा Lean छान। तेस्रो पाइलामा समस्यालाई त्यो औजारको भाषामा encode गर। चौथो पाइलामा उत्तरको अर्थ भन, र sat भए model ले उदाहरण वा counterexample दिन्छ, unsat भए त्यस्तो अवस्था कहीँ छैन, र unknown भए औजारले निर्णय गर्न सकेन। पाँचौं पाइलामा soundness र completeness का सीमा अनि trade-off स्पष्ट भन।
@end

[sanji]"मानौं प्रश्न आयो, यो integer को जोडमा overflow हुन सक्छ कि सक्दैन?"[/] सान्जीले भन्यो। [sanji]"पहिले property भन, कि कुनै पनि input मा जोड सीमाभित्र रहन्छ। त्यसपछि Z3 छान, किनभने यो constraint को प्रश्न हो। bit-vector ले encode गर, र property को negation solver लाई दे।"[/]

@recall llm-loop | व्यापारी र जाँचकर्ताको यो loop फेरि सुन, र यसपटक जाँचकर्ताको कलम मनमा राख।

@read teach
यसलाई trusted computing base भनिन्छ। Lean को kernel सानो छ, र त्यसले proof term मात्र जाँच्छ। tactic, automation, र LLM जति ठूला र जटिल भए पनि, तिनले बनाएको proof अन्तमा त्यही सानो kernel बाट पार हुनुपर्छ।

त्यसैले LLM ले गल्ती गर्‍यो भने पनि खतरा हुँदैन। गलत proof kernel मा अड्किन्छ, र कहिल्यै theorem बन्दैन।

[robin]"तर एउटा ठाउँमा kernel ले पनि बचाउँदैन।"[/] रोबिनले भनिन्। [robin]"theorem को कथन आफैं गलत भयो भने, kernel ले गलत कुराको सही proof स्वीकार गर्छ। LLM ले कहिलेकाहीँ प्रश्नलाई नै सजिलो बनाइदिन्छ, र त्यो छल पत्ता लगाउन मान्छेले specification पढ्नैपर्छ।"[/]

अर्को खतरा sorry नामको शब्द हो। Lean मा sorry लेख्यौ भने proof अधुरो भए पनि file compile हुन्छ। त्यसैले LLM ले लेखेको proof मा sorry वा नयाँ axiom छ कि छैन भनेर सधैं जाँच गर।

ब्रुकले दीपस्तम्भ हेर्दै भन्यो — [brook]"त्यो बत्ती कहिल्यै सुत्दैन। तर मान्छेले त्यसलाई हरेक रात जाँच्छन्।"[/]

@read teach
उद्योगमा पनि यस्तै हुन्छ। proof एकपटक गरेर सकिँदैन। code फेरिन्छ, र हरेक परिवर्तनपछि proof फेरि चलाउनुपर्छ। त्यसैले ठूला कम्पनीले solver लाई continuous integration मा राख्छन्।

AWS मा हरेक दिन लाखौं SMT query चल्छन्। तिनलाई छिटो राख्न इन्जिनियरहरू सूत्रलाई सरल बनाउँछन्, timeout राख्छन्, र unknown आयो भने सुरक्षित बाटो रोज्छन्।

[franky]"unknown आयो भने सुरक्षित बाटो भनेको के हो?"[/] फ्र्याङ्कीले सोध्यो।
