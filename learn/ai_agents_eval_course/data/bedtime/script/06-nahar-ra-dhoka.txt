# ६ — नहर र ढोकाको सहर: Workflow, Orchestration, DSPy र MCP

छैटौं टापु पानीमाथि बसेको एउटा सहर हो। यहाँ सडक छैनन्, नहर छन्। नहरका बीचमा ठूला काठका ढोका छन्, र हरेक ढोकाले पानीको सतह मिलाएर डुङ्गालाई अर्को खण्डमा पठाउँछ।

सहरको बीचमा एउटा अग्लो नियन्त्रण घर छ। त्यहाँ एउटा पुरानो ढोका पालेले ठूलो नक्सा हेर्दै हरेक डुङ्गालाई बाटो देखाउँछ।

ढोका पालेले टोलीलाई भने — [sage]"यो सहरमा कुनै डुङ्गा आफूखुसी हिँड्दैन। हरेक डुङ्गा एउटा खण्डबाट अर्को खण्डमा जान्छ, र हरेक ढोकामा एउटा नियम छ।"[/]

@read teach
यही नै workflow orchestration हो। काम धेरै पाइलामा बाँडिन्छ, र ती पाइला एउटा graph बन्छन्। हरेक पाइलालाई node भनिन्छ। node हरूलाई जोड्ने बाटोलाई edge भनिन्छ। अनि सबै node ले सँगै बोक्ने सामानको पोकोलाई state भनिन्छ। LangGraph जस्ता framework ले ठ्याक्कै यही ढाँचा दिन्छन्।

[nami]"यो state machine हो।"[/] नामीले भनिन्। [nami]"डुङ्गा कुनै समयमा एउटै खण्डमा हुन्छ। ढोका खुल्छ कि खुल्दैन भन्ने कुरा डुङ्गाको अवस्था हेरेर तय हुन्छ। त्यसलाई conditional edge भनिन्छ।"[/]

@algo workflow
workflow graph को विधि यस्तो छ। पहिलो चरणमा एउटा state object परिभाषित गर, जसमा messages, बीचका नतिजा र गन्ती हुन्छन्। दोस्रो चरणमा हरेक पाइलालाई node बनाऊ, जसले state पढ्छ र state को केही भाग फर्काउँछ। तेस्रो चरणमा node हरूलाई edge ले जोड, र बाटो छुट्टिने ठाउँमा state हेरेर अर्को node छान्ने conditional edge राख। चौथो चरणमा start node बाट चलाऊ, र हरेक node पछि state को checkpoint सुरक्षित गर। पाँचौं चरणमा अस्थायी error आयो भने exponential backoff सहित retry गर, र स्थायी error आयो भने error को बाटोतिर पठाऊ। छैटौं चरणमा end node पुगेपछि रोक, र घुमिरहने बाटोमा सधैं अधिकतम चक्रको सीमा राख।
@end

[chopper]"checkpoint किन चाहिन्छ?"[/] चोपरले सोध्यो।

ढोका पालेले मुस्कुराएर भने — [sage]"आँधी आयो र सहरको बत्ती गयो भने, म हरेक डुङ्गा कुन खण्डमा थियो भनेर यो किताबमा हेर्छु। अनि डुङ्गालाई त्यहीँबाट अघि बढाउँछु। सुरुदेखि फेरि चलाउनु पर्दैन।"[/]

@read teach
checkpoint ले तीन काम गर्छ। प्रक्रिया बीचमा मर्यो भने त्यहीँबाट फेरि सुरु गर्न दिन्छ। मानिसको स्वीकृति चाहिने ठाउँमा graph रोकेर पर्खन दिन्छ, जसलाई human in the loop भनिन्छ। अनि पछि debug गर्दा हरेक पाइलाको state हेर्न दिन्छ।

@recall workflow | नहरको विधि फेरि एकपटक सुन।

सहरका सबै ढोका एउटै किसिमका थिए। जुनसुकै देशबाट आएको डुङ्गा पनि त्यही ढोकामा अटाउँथ्यो। फ्र्याङ्कीले त्यो देखेर भन्यो — [franky]"यो त सुपर मानक हो!"[/]

@read teach
tool जोड्ने संसारमा त्यस्तै एउटा मानक छ, र त्यसको नाम MCP हो। MCP को पूरा नाम model context protocol हो। पहिले हरेक app ले हरेक tool का लागि छुट्टै जोड लेख्थ्यो। अब tool बनाउनेले एउटा MCP server बनाउँछ, र जुनसुकै MCP client ले त्यसलाई प्रयोग गर्न सक्छ।

@algo mcp
MCP को विधि यस्तो छ। MCP server ले आफ्ना tools, resources र prompts प्रस्तुत गर्छ। host भित्रको MCP client ले server सँग stdio वा HTTP माथि JSON-RPC सन्देशले जोड्छ, र सुरुमा initialize गरेर दुवैले आफ्ना क्षमता साट्छन्। त्यसपछि client ले tools/list बोलाएर हरेक tool को नाम, description र input_schema पाउँछ। host ले ती tool model लाई दिन्छ। model ले tool_use माग्यो भने client ले tools/call बोलाउँछ, र server को नतिजा tool_result बनेर model कहाँ फर्कन्छ।
@end

[usopp]"त्यसो भए MCP भनेको agent loop नै हो?"[/] उसोपले सोध्यो।

[robin]"होइन।"[/] रोबिनले भनिन्। [robin]"agent loop त्यही रहन्छ, जुन तेस्रो टापुमा सिक्यौं। MCP ले tool कहाँबाट आउँछ र कसरी बोलाइन्छ भन्ने कुरा मात्र मानक बनाउँछ। tool चाहिँ एउटा process मा हुन्छ, र model अर्कै ठाउँमा हुन्छ, तर बीचको भाषा एउटै हुन्छ।"[/]

@recall mcp | मानक ढोकाको विधि फेरि एकपटक सुन।

रात पर्दै गयो, र नहरका ढोका एक एक गर्दै बन्द भए। ढोका पालेले आफ्नो किताबमा अन्तिम checkpoint लेखे, र बत्ती मधुरो पारे।

@read hush
सबै डुङ्गा आफ्नै खण्डमा सुरक्षित छन्। भोलि बिहान ती जहाँ रोकिएका थिए, त्यहीँबाट फेरि हिँड्छन्।

@recall workflow | नहर छाड्नुअघि workflow को विधि अन्तिम पटक सुन।

@recall mcp | अनि MCP को विधि पनि अन्तिम पटक सुन।

@tier medium

रोबिनले DSPy को कुरा सुनाइन्। [robin]"DSPy मा prompt हातले लेखिँदैन।"[/] उनले भनिन्। [robin]"पहिले signature लेखिन्छ, जसले input र output को नाम मात्र भन्छ। त्यसपछि chain of thought वा retrieve जस्ता module हरू जोडिन्छन्। अनि एउटा metric र केही उदाहरण दिइन्छ, र optimizer ले prompt र few-shot उदाहरण आफैं खोजेर compile गर्छ। यसको मूल विचार यो हो कि prompt पनि metric ले नापेर सुधारिने चीज हो।"[/]

@read teach
retry को बारेमा एउटा कुरा सधैं सम्झ। retry गर्ने पाइला idempotent हुनुपर्छ। idempotent भनेको उही काम दुई पटक गर्दा पनि नतिजा एक पटक गरेजस्तै हुनु हो। इमेल पठाउने वा पैसा तिर्ने node दुई पटक चल्यो भने दुई इमेल जान्छन्। त्यसैले यस्तो काममा idempotency key राख, र पहिले नै भइसकेको काम फेरि नगर।

@tier long

[zoro]"timeout चाहिँ कहाँ राख्ने?"[/] जोरोले सोध्यो।

[nami]"हरेक बाहिरी call मा राख।"[/] नामीले भनिन्। [nami]"model call, tool call, र वेब call सबैमा timeout राख। timeout नभए एउटा अड्किएको call ले सिङ्गो workflow रोक्छ। अनि हरेक node को समय र नतिजा trace मा लेख, ताकि कुन ढोकामा डुङ्गा अड्कियो भनेर पछि देखियोस्।"[/]

@read hush
नहरको पानी अब स्थिर छ। ढोका पाले आफ्नो कुर्सीमा बसेर निदाए, र सहर पूरै चुप भयो।
