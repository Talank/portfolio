# १२ — हजार डुङ्गाको बेडा: Parallelism, Rate Limit, Cache, Batch API र Sandbox

बाह्रौं टापुमा एउटा व्यस्त बन्दरगाह छ। तर यो बन्दरगाहमा डुङ्गा बाँध्ने खुट्टी जम्मा आठ वटा मात्र छन्। अनि आज टोलीले हजार वटा सन्देश पठाउनु छ।

लुफीले भन्यो — [luffy]"सबै हजार डुङ्गा एकै पटक पठाऊ! छिटो सकिन्छ!"[/]

नामीले टाउको हल्लाइन्। [nami]"सबै एकै पटक गए भने बन्दरगाहको ढोकामा जाम हुन्छ।"[/] उनले भनिन्। [nami]"बन्दरगाहको मालिकले धेरैजसोलाई फर्काइदिन्छ, र तिनले फेरि आउँदा झन् ठूलो जाम हुन्छ।"[/]

@read teach
ठूलो eval मा ठ्याक्कै यस्तै हुन्छ। हजारौं प्रश्न छन्, र हरेक प्रश्नमा model call छ। एउटा एउटा गरेर चलायौ भने रातभरि लाग्छ। सबै एकै पटक चलायौ भने API ले rate limit को error दिन्छ, र त्यसको code चार सय उनन्तीस हो। त्यसैले बीचको बाटो चाहिन्छ, र त्यो async concurrency हो।

@read teach
async मा धेरै request एकै पटक उडानमा हुन्छन्, र कुनै request को जवाफ पर्खँदा program रोकिँदैन। तर एकै पटक कति उडानमा हुन्छन् भनेर semaphore ले सीमा राख्छ। semaphore भनेको खुट्टीको गन्ती हो। आठ वटा खुट्टी छन् भने आठ वटा डुङ्गा मात्र भित्र पस्छन्, र एउटा निस्केपछि मात्र अर्को पस्छ।

@algo scale
ठूलो eval चलाउने विधि यस्तो छ। पहिलो चरणमा हरेक call को cache key बनाऊ, जुन model, prompt र सबै parameter जोडेर निकालेको hash हो। दोस्रो चरणमा त्यो key cache मा छ भने API नबोलाई cache को नतिजा फर्काऊ। तेस्रो चरणमा cache मा छैन भने async semaphore लेऊ, जसले एकै पटक N वटा भन्दा बढी request चल्न दिँदैन। चौथो चरणमा request पठाऊ, र चार सय उनन्तीस वा पाँच सय भन्दा माथिको error आयो भने exponential backoff सहित retry गर। प्रतीक्षाको समय आधार समय गुणा दुईको attempt घात हुन्छ, त्यसमा अलिकति random jitter जोडिन्छ, र त्यो एउटा अधिकतम सीमाभन्दा माथि जाँदैन। पाँचौं चरणमा सफल नतिजालाई cache मा राख, र JSONL फाइलमा तुरुन्तै एउटा line थप। यसरी run बीचमा मरे पनि फेरि चलाउँदा सकिएका काम cache बाट आउँछन्, र बाँकी काम मात्र चल्छन्।
@end

[usopp]"jitter किन चाहिन्छ?"[/] उसोपले सोध्यो।

[nami]"सय वटा डुङ्गा एकै पल फर्काइए भन।"[/] नामीले भनिन्। [nami]"सबैले ठ्याक्कै दुई सेकेन्ड पर्खे भने सबै फेरि एकै पल आउँछन्, र फेरि जाम हुन्छ। अलिकति random समय थप्यो भने डुङ्गाहरू छरिएर आउँछन्। अनि server ले Retry-After भन्ने header पठायो भने त्यही समय मान।"[/]

@read hush
पर्खाइ दोब्बर हुँदै जान्छ। एक, दुई, चार, आठ सेकेन्ड। अनि हरेक पर्खाइमा अलिकति हावा मिसिन्छ, ताकि कोही पनि अर्कोसँग ठोक्किँदैन।

@recall scale | बन्दरगाहको विधि फेरि एकपटक सुन।

रोबिनले एउटा मोटो लगबुक खोलिन्। [robin]"यो हाम्रो cache हो।"[/] उनले भनिन्। [robin]"हरेक सन्देशको छाप यहाँ लेखिन्छ। उही सन्देश फेरि पठाउनुपर्यो भने पहिले यहाँ हेर्छौं। उत्तर पहिले नै छ भने डुङ्गा पठाउनै पर्दैन।"[/]

@read teach
cache key मा के के पर्छ भन्ने कुरा महत्त्वपूर्ण छ। model को नाम, system prompt, messages, temperature, max_tokens, र tool को परिभाषा सबै key मा पर्नुपर्छ। एउटा पनि छुट्यो भने setting बदल्दा पनि पुरानै उत्तर आउँछ, र तिमीले गलत कुरा नाप्छौ। temperature शून्यभन्दा माथि राखेर धेरै नमुना चाहिएको बेला नमुनाको क्रम सङ्ख्या पनि key मा राख।

बन्दरगाहको अर्को छेउमा एउटा ठूलो मालवाहक जहाज थियो। त्यसका मालिकले भने — [sage]"हतार छैन भने सबै सन्देश मलाई देऊ। म रातभरि बिस्तारै पुर्याइदिन्छु, र आधा भाडा मात्र लिन्छु।"[/]

@read teach
त्यो Batch API हो। तुरुन्तै उत्तर नचाहिने eval मा हजारौं request एउटै फाइलमा राखेर पठाइन्छ। ती केही घण्टाभित्र सकिन्छन्, र मूल्य झन्डै आधा हुन्छ। हरेक request मा custom id राख, किनभने उत्तरहरू पठाएकै क्रममा आउँदैनन्, र id ले नै उत्तरलाई प्रश्नसँग जोड्छ।

@read teach
code जाँच्ने eval मा अर्को कुरा थपिन्छ। model ले लेखेको code सधैं sandbox भित्र चलाइन्छ। हरेक नमुनाका लागि सफा container, समयको सीमा, memory को सीमा, र network बन्द हुन्छ। container सुरु गर्न समय लाग्छ, त्यसैले container को pool तयार राखिन्छ, र एउटा काम सकिएपछि त्यसलाई सफा पारेर फेरि प्रयोग गरिन्छ।

हजार डुङ्गा बिस्तारै, आठ आठ गरेर बन्दरगाहभित्र पसे, र बाहिर निस्के। कुनै जाम भएन। लगबुक भरिँदै गयो।

@recall scale | बन्दरगाह छाड्नुअघि विधि अन्तिम पटक सुन।

@tier medium

फ्र्याङ्कीले एउटा कुरा थप्यो। [franky]"हरेक नतिजा तुरुन्तै फाइलमा लेख।"[/] उसले भन्यो। [franky]"सबै काम सकिएपछि मात्र लेख्ने योजना बनायौ भने बीचमा एउटा error आउँदा सबै हराउँछ। JSONL मा एउटा नतिजा एउटा line हुन्छ, त्यसैले बीचमा रोकिए पनि फाइल बिग्रिँदैन।"[/]

@read teach
खर्च पनि नाप। हरेक call को input token, output token, cache बाट पढिएका token, र समय लेख। run सुरु गर्नुअघि दस वटा प्रश्नमा चलाएर पूरा run को खर्च अनुमान गर। अनि खर्चको माथिल्लो सीमा राख, ताकि गल्तीले लेखिएको loop ले रातभरि पैसा नसकोस्।

@tier long

[chopper]"concurrency कति राख्ने?"[/] चोपरले सोध्यो।

[nami]"rate limit हेरेर राख।"[/] नामीले भनिन्। [nami]"API ले प्रति मिनेट request को सीमा र प्रति मिनेट token को सीमा दिन्छ। औसत request ले कति token लिन्छ र कति समय लिन्छ भनेर नाप, अनि सीमाभित्र अटाउने concurrency छान। चार सय उनन्तीस धेरै आयो भने concurrency घटाऊ।"[/]

[zoro]"एउटा प्रश्न सधैं असफल भयो भने?"[/] जोरोले सोध्यो।

[nami]"retry को सङ्ख्या सीमित राख, र त्यसपछि त्यो प्रश्नलाई error भनेर लेख।"[/] नामीले भनिन्। [nami]"error भएका प्रश्नलाई चुपचाप शून्य अङ्क नदेऊ, र चुपचाप हटाउने काम पनि नगर। कति प्रश्न error भए भनेर रिपोर्टमा छुट्टै लेख।"[/]
