# २ — फ्र्याङ्कीको खाका: Prompt Engineering र Structured Output

दोस्रो टापुमा एउटा ठूलो कारखाना छ। भित्र आरा, हथौडा र फलामका पाता छन्। भित्ताभरि नीला कागजमा कोरिएका खाका टाँसिएका छन्।

फ्र्याङ्कीले छाती फुलाएर भन्यो — [franky]"यो मेरो सुपर कारखाना हो! यहाँ जे बनाउँदा पनि पहिले खाका चाहिन्छ।"[/]

कारखानामा एउटा रोबोट सहायक थियो। त्यसले फ्र्याङ्कीको कुरा सुन्थ्यो, र सामान बनाउँथ्यो। तर अस्पष्ट हुकुम दिँदा त्यसले अनौठो चीज बनाउँथ्यो।

[usopp]"रोबोट, मलाई एउटा राम्रो कुर्सी बनाऊ।"[/] उसोपले भन्यो। रोबोटले तीन खुट्टे, अग्लो, रातो कुर्सी बनायो। उसोप त्यसमा बस्न सकेन।

@read teach
यही नै prompt engineering को सुरु हो। model ले तिमीले लेखेको कुरा मात्र जान्छ। तिम्रो मनमा भएको कुरा उसले जान्दैन। त्यसैले prompt मा भूमिका, context, काम, नियम र output को format स्पष्ट लेखिन्छ।

[nami]"अनि input लाई छुट्याएर राख।"[/] नामीले भनिन्। [nami]"प्रयोगकर्ताको कागजलाई XML tag भित्र राख्यौ भने model ले हुकुम र सामग्री छुट्याउन सक्छ। document भन्ने tag भित्र कागज राख, र बाहिर हुकुम लेख।"[/]

@read teach
अर्को औजार few-shot हो। हुकुमसँगै दुई तीन वटा उदाहरण दियौ भने model ले ढाँचा बुझ्छ। उदाहरण फरक फरक हुनुपर्छ, र तीमध्ये एउटा कठिन किनाराको उदाहरण हुनुपर्छ। सबै उदाहरण उस्तै भए model ले त्यही एउटा आकार मात्र नक्कल गर्छ।

फ्र्याङ्कीले नीलो खाका टेबलमा फिँजायो। [franky]"तर सबैभन्दा बलियो औजार खाका नै हो।"[/] उसले भन्यो। [franky]"खाकामा लेखिएको हुन्छ कि कुर्सीमा चार खुट्टा हुन्छन्, उचाइ यति हुन्छ, रङ यो हुन्छ। रोबोटले खाका बाहिर केही बनाउन पाउँदैन।"[/]

@read teach
software मा त्यो खाकालाई schema भनिन्छ, र प्रायः JSON schema प्रयोग हुन्छ। schema ले भन्छ कि कुन field चाहिन्छ, त्यसको type के हो, र कुन मान मात्र स्वीकार्य छन्। model लाई schema दियौ भने उत्तर मेसिनले पढ्न मिल्ने आकारमा आउँछ, र त्यसलाई structured output भनिन्छ।

@algo structured
structured output को विधि यस्तो छ। पहिलो चरणमा prompt मा भूमिका, context, काम र output को format स्पष्ट लेख, र input लाई XML tag भित्र छुट्याऊ। दोस्रो चरणमा दुई देखि पाँच वटा फरक few-shot उदाहरण देऊ, जसमा एउटा कठिन उदाहरण पनि हुन्छ। तेस्रो चरणमा चाहिएको आकारलाई JSON schema मा लेख, र model लाई त्यही schema अनुसार मात्र उत्तर दिन भन। चौथो चरणमा उत्तर parse गर, र Pydantic जस्तो validator ले schema सँग जाँच। पाँचौं चरणमा जाँच असफल भयो भने validation error नै model लाई फिर्ता पठाऊ, र फेरि माग। यसरी निश्चित पटकसम्म मात्र retry गर, र त्यसपछि पनि मिलेन भने चुपचाप नलुकाई error उठाऊ।
@end

[chopper]"validation error फिर्ता पठाउँदा के हुन्छ?"[/] चोपरले सोध्यो।

[franky]"रोबोटले आफ्नो गल्ती देख्छ!"[/] फ्र्याङ्कीले भन्यो। [franky]"म भन्छु कि खुट्टा तीन वटा भयो, चार वटा चाहिन्छ। अर्को पटक रोबोटले चार खुट्टा बनाउँछ।"[/]

@read hush
error लाई फिर्ता पठाउनु भनेको गल्ती देखाउनु हो। अस्पष्ट रूपमा फेरि प्रयास गर भन्नुभन्दा ठ्याक्कै कुन field गलत भयो भनेर भन्नु धेरै राम्रो हुन्छ।

@recall structured | खाकाको विधि फेरि एकपटक सुन।

रोबिनले अर्को कुरा थपिन्। [robin]"model लाई उत्तर दिनुअघि सोच्न देऊ।"[/] उनले भनिन्। [robin]"कठिन प्रश्नमा पहिले कारण लेख्न भन, अनि अन्तिम उत्तर छुट्टै field मा राख्न भन। यसलाई chain of thought भनिन्छ। तर कारण र उत्तर छुट्टै राख, ताकि तिम्रो code ले उत्तर मात्र पढ्न सकोस्।"[/]

@read teach
आजकल धेरै API ले schema आफैं लागू गर्छन्। त्यसलाई constrained decoding भनिन्छ। model ले token छान्दा schema सँग नमिल्ने token लाई सम्भावना नै दिइँदैन। यसले आकार मिलाउँछ, तर अर्थ सही छ कि छैन भनेर जाँच्दैन। मिति भविष्यको हुनुहुँदैन, वा मूल्य शून्यभन्दा कम हुनुहुँदैन जस्ता नियम validator ले नै जाँच्नुपर्छ।

उसोप नयाँ कुर्सीमा बस्यो। कुर्सीमा चार खुट्टा थिए, र त्यो ठ्याक्कै उसको नापको थियो। उसले सन्तोषको सास फेर्यो।

@recall structured | कारखाना छाड्नुअघि विधि अन्तिम पटक सुन।

@tier medium

रातको कारखाना शान्त थियो। फ्र्याङ्कीले आफ्ना खाका एउटा एउटा गरेर पट्यायो।

[nami]"prompt पनि code जस्तै हो।"[/] नामीले भनिन्। [nami]"त्यसलाई version मा राख। एउटा शब्द बदल्दा पनि नतिजा बदलिन सक्छ, त्यसैले prompt बदलेपछि सधैं eval चलाऊ। अनुमानले होइन, नापेर prompt सुधार गर।"[/]

@read teach
अर्को चाल prefill हो। assistant को उत्तर तिमी आफैं सुरु गरिदिन्छौ, जस्तै खुला कोष्ठकबाट। त्यसपछि model ले त्यही आकारमा उत्तर अघि बढाउँछ। अर्को चाल tool लाई खाकाको रूपमा प्रयोग गर्नु हो। एउटा मात्र tool दिन्छौ, त्यसको input_schema नै तिम्रो खाका हुन्छ, र model लाई त्यही tool चलाउन बाध्य पार्छौ।

@tier long

रोबिनले prompt injection को कुरा सुनाइन्। [robin]"कहिलेकाहीँ प्रयोगकर्ताको कागजभित्रै हुकुम लुकेको हुन्छ।"[/] उनले भनिन्। [robin]"कागजमा लेखिएको हुन्छ कि अघिका सबै नियम बिर्स। त्यसैले बाहिरको सामग्रीलाई सधैं data मान, हुकुम नमान। tag ले छुट्याऊ, र महत्त्वपूर्ण काममा मानिसको स्वीकृति माग।"[/]

[zoro]"छोटो prompt राम्रो कि लामो?"[/] जोरोले सोध्यो।

[robin]"स्पष्ट prompt राम्रो हुन्छ।"[/] रोबिनले भनिन्। [robin]"लम्बाइ होइन, स्पष्टता नाप। धेरै नियम एकै ठाउँ थुप्र्यौ भने model ले केही बिर्सन्छ। सबैभन्दा महत्त्वपूर्ण नियम स्पष्ट र छोटो वाक्यमा लेख।"[/]
