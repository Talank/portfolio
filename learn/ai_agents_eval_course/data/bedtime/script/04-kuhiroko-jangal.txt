# ४ — कुहिरोको जङ्गल: ReAct, Plan-and-Execute, Reflection र Multi-Agent

चौथो टापुभरि बाक्लो जङ्गल छ। रूखहरू अग्ला छन्, र बीचमा सधैं कुहिरो लागेको हुन्छ। एक पाइलाभन्दा टाढा केही देखिँदैन।

जोरो सबैभन्दा पहिले जङ्गलमा पस्यो। उसले कतै नहेरी सिधै हिँड्यो, र अलि बेरमा उही ठाउँमा फर्केर आयो। ऊ तीन पटक उही रूखको फेदमा पुग्यो।

[nami]"जोरो, तिमी सोच्दै नसोची हिँड्छौ।"[/] नामीले भनिन्। [nami]"यो जङ्गलमा हरेक पाइलापछि रोकिनुपर्छ। पहिले सोच, अनि हिँड, अनि हेर।"[/]

@read teach
नामीले भनेको तरिकाको नाम ReAct हो। ReAct भनेको reasoning र acting को मिलन हो। model ले पहिले आफ्नो सोच लेख्छ, त्यसपछि एउटा काम गर्छ, अनि त्यस कामको नतिजा हेर्छ। सोच लेख्दा model ले आफ्नो बाटो आफैं देख्छ, र नतिजा हेर्दा उसले वास्तविक संसारबाट सिक्छ।

@algo react
ReAct को विधि यस्तो छ। पहिलो चरणमा model ले Thought लेख्छ, जसमा अहिले के थाहा छ र अब के चाहिन्छ भनेर सोच्छ। दोस्रो चरणमा model ले Action छान्छ, अर्थात् एउटा tool र त्यसको input छान्छ। तेस्रो चरणमा code ले त्यो tool चलाउँछ, र नतिजा Observation बनेर model कहाँ फर्कन्छ। चौथो चरणमा model ले Observation पढेर फेरि Thought लेख्छ। यो Thought, Action र Observation को चक्र दोहोरिइरहन्छ। model ले Final Answer लेखेपछि, वा पाइलाको सीमा पुगेपछि, चक्र रोकिन्छ।
@end

जोरोले यसपटक त्यसै गर्यो। उसले सोच्यो कि खोला पूर्वतिर बग्छ। उसले कान थाप्यो। उसले पानीको आवाज सुन्यो। अनि ऊ आवाजतिर हिँड्यो।

@read hush
सोच, काम, र नतिजा। फेरि सोच, फेरि काम, र फेरि नतिजा। कुहिरोमा बाटो यसरी नै बन्छ।

रोबिनले अर्को तरिका सुनाइन्। [robin]"कहिलेकाहीँ पहिले पूरै योजना बनाउनु राम्रो हुन्छ।"[/] उनले भनिन्। [robin]"यसलाई plan and execute भनिन्छ। planner ले काम सानो सानो पाइलामा टुक्र्याउँछ, र सूची बनाउँछ। executor ले ती पाइला एउटा एउटा गरेर चलाउँछ। कुनै पाइला असफल भयो भने planner ले बाँकी योजना फेरि बनाउँछ, र यसलाई replanning भनिन्छ।"[/]

@read teach
ReAct र plan and execute को फरक सम्झ। ReAct ले हरेक पाइलामा मात्र सोच्छ, त्यसैले नयाँ कुरा आउँदा छिटो मोडिन्छ, तर लामो काममा लक्ष्य बिर्सन सक्छ। plan and execute ले सुरुमै ठूलो चित्र बनाउँछ, त्यसैले लामो काममा बाटो छोड्दैन, तर योजना गलत भयो भने सच्याउन replanning चाहिन्छ।

@recall react | कुहिरोमा हिँड्ने विधि फेरि एकपटक सुन।

उसोपले एउटा ढुङ्गामा बसेर नक्सा कोर्यो। कोरिसकेपछि उसले आफ्नै नक्सा फेरि हेर्यो, र एउटा गल्ती भेट्टायो। [usopp]"यहाँ खोला उल्टो दिशामा कोरेको रहेछु।"[/] उसले भन्यो, र सच्यायो।

@read teach
यो तेस्रो तरिका हो, र यसलाई reflection भनिन्छ। पहिले model ले उत्तर बनाउँछ। त्यसपछि उही model, वा अर्को model, ले त्यो उत्तरको आलोचना लेख्छ। अनि त्यो आलोचना पढेर उत्तर सुधारिन्छ। यो चक्र दुई तीन पटक चल्छ। test चलाउने वा validator चलाउने जस्तो बाहिरी प्रमाण भयो भने reflection धेरै बलियो हुन्छ।

जिम्बेले शान्त स्वरमा भन्यो — [warm]"एक्लै सबै काम गर्न गाह्रो हुन्छ। टोली बाँड्नु पनि एउटा तरिका हो।"[/]

@read teach
चौथो तरिका multi-agent हो। एउटा orchestrator ले काम टुक्र्याउँछ, र हरेक टुक्रा छुट्टै worker agent लाई दिन्छ। हरेक worker को आफ्नै सानो context हुन्छ, र आफ्नै tool हुन्छन्। worker हरूले नतिजा फर्काउँछन्, र orchestrator ले ती जोडेर अन्तिम उत्तर बनाउँछ। यसले ठूलो खोजलाई समानान्तर बनाउँछ, तर token धेरै खर्च हुन्छ, र agent हरूबीच कुरा हराउन सक्छ।

नामीले चेतावनी दिइन्। [nami]"सबैभन्दा सजिलो तरिका पहिले प्रयोग गर।"[/] उनले भनिन्। [nami]"एउटा राम्रो prompt ले काम चल्छ भने agent नबनाऊ। निश्चित पाइला भएको workflow ले काम चल्छ भने स्वतन्त्र agent नबनाऊ। जटिलता तब मात्र थप, जब नापेर देख्छौ कि त्यसले नतिजा सुधार्छ।"[/]

जोरो अन्त्यमा खोलाको किनारमा पुग्यो। ऊ एउटा रूखमा अडेस लगाएर बस्यो, र तुरुन्तै निदायो।

@recall react | जङ्गल छाड्नुअघि ReAct को चक्र अन्तिम पटक सुन।

@tier medium

रोबिनले workflow का केही ढाँचा गनाइन्। [robin]"पहिलो ढाँचा prompt chaining हो।"[/] उनले भनिन्। [robin]"एउटा call को output अर्को call को input बन्छ, र बीचमा code ले जाँच गर्छ। दोस्रो ढाँचा routing हो, जसमा पहिले प्रश्नको किसिम छुट्याइन्छ, अनि सही बाटोमा पठाइन्छ। तेस्रो ढाँचा parallelization हो, जसमा एउटै कामका टुक्रा सँगै चल्छन्, वा एउटै काम धेरै पटक चलाएर बहुमत लिइन्छ। चौथो ढाँचा evaluator optimizer हो, जसमा एउटाले बनाउँछ र अर्कोले जाँच्छ।"[/]

@read teach
workflow र agent को फरक यसरी भन। workflow मा पाइलाको क्रम code ले तय गर्छ। agent मा पाइलाको क्रम model आफैंले तय गर्छ। workflow भरपर्दो र सस्तो हुन्छ। agent लचिलो हुन्छ, तर त्यसको व्यवहार नाप्न र जाँच्न गाह्रो हुन्छ।

@tier long

चोपरले सोध्यो — [chopper]"reflection ले जहिले पनि उत्तर सुधार्छ?"[/]

[robin]"सधैं सुधार्दैन।"[/] रोबिनले भनिन्। [robin]"बाहिरी प्रमाण बिना model ले आफ्नै गल्ती प्रायः देख्दैन, र कहिलेकाहीँ सही उत्तरलाई पनि बिगार्छ। त्यसैले reflection को साँचो फाइदा test, compiler वा validator जस्तो वास्तविक संकेतबाट आउँछ। अनि यसको फाइदा पनि eval ले नापेर मात्र विश्वास गर।"[/]

@read hush
कुहिरो अझै जङ्गलमा अडिएको छ। तर अब टोलीलाई डर छैन, किनभने उनीहरूले रोकिएर सोच्न सिकेका छन्।
