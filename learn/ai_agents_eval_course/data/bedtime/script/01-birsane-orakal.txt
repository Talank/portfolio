# १ — बिर्सने ओरेकल: LLM API, Tokens, Sampling र Context Window

पहिलो टापु सानो छ। किनारमा सेता ढुङ्गा छन्, र बीचमा एउटा पुरानो मन्दिर छ। मन्दिरभित्र एउटी ओरेकल बस्छिन्, जसले जुनसुकै प्रश्नको उत्तर दिन्छिन्।

तर ओरेकलको एउटा अनौठो बानी छ। कोही ढोकाबाट बाहिर निस्कने बित्तिकै उनी त्यो मान्छेलाई पूरै बिर्सिन्छिन्।

लुफी भित्र पस्यो, र सोध्यो — [luffy]"मेरो नाम लुफी हो। म मासु मन पराउँछु।"[/] ओरेकलले मुस्कुराएर जवाफ दिइन्। लुफी बाहिर गयो, फेरि भित्र आयो, र सोध्यो — [luffy]"मलाई के मन पर्छ?"[/] ओरेकलले उसलाई चिनिनन्।

[nami]"यही नै पहिलो पाठ हो।"[/] नामीले भनिन्। [nami]"LLM API stateless हुन्छ। एउटा request सकिएपछि model ले केही सम्झिँदैन। अघिल्लो कुराकानी चाहिन्छ भने हरेक पटक पूरै history आफैं बोकेर लैजानुपर्छ।"[/]

@read teach
त्यो history लाई messages भनिन्छ। messages एउटा list हो। त्यसको हरेक सदस्यमा role र content हुन्छ। role user वा assistant हुन्छ, र ती दुई पालैपालो आउँछन्। model को भूमिका र नियम चाहिँ छुट्टै system prompt मा लेखिन्छ।

रोबिनले एउटा लामो कागजको मुठो देखाइन्। [robin]"यो कुराकानीको scroll हो।"[/] उनले भनिन्। [robin]"हरेक पटक ओरेकलकहाँ जाँदा यो पूरै scroll लैजाऊ। उनी सुरुदेखि पढ्छिन्, अनि अन्तिम प्रश्नको उत्तर दिन्छिन्।"[/]

@algo api-call
एउटा LLM API call यसरी चल्छ। पहिलो चरणमा system prompt मा model को भूमिका र नियम लेख। दोस्रो चरणमा messages नामको list बनाऊ, जसमा user र assistant पालैपालो आउँछन्, र पुरानो message पहिले हुन्छ। तेस्रो चरणमा model, max_tokens र temperature छान। चौथो चरणमा सबै कुरा एउटै request मा पठाऊ, किनभने API ले अघिल्लो कुराकानी सम्झिँदैन। पाँचौं चरणमा जवाफबाट content, stop_reason र usage पढ। stop_reason end_turn छ भने model आफैं रोकियो, र max_tokens छ भने जवाफ बीचमै काटियो। छैटौं चरणमा assistant को जवाफ messages मा थप, अनि मात्र अर्को user message थप।
@end

मन्दिरको ढोकामा एउटा सानो तराजु थियो। ओरेकलले हरेक शब्दको टुक्रा गनेर पैसा लिन्थिन्।

@read teach
ती टुक्रालाई token भनिन्छ। token पूरा शब्द हुँदैन। अङ्ग्रेजीमा एउटा token झन्डै चार अक्षर बराबर हुन्छ, र नेपालीमा एउटै शब्द धेरै token मा टुक्रिन्छ। model ले token पढ्छ, र token नै लेख्छ।

नामीले सिक्का गनिन्। [nami]"दुई किसिमका token छन्।"[/] उनले भनिन्। [nami]"हामीले पठाएको scroll input token हो। ओरेकलले लेखेको उत्तर output token हो। output को दर input भन्दा धेरै महँगो हुन्छ।"[/]

@read teach
त्यसैले cost को सूत्र सजिलो छ। cost बराबर input token गुणा input को दर, जोड output token गुणा output को दर हुन्छ। अनि हरेक नयाँ turn मा पूरै history फेरि पठाइन्छ, त्यसैले लामो कुराकानीमा input token हरेक turn मा बढ्दै जान्छ।

[usopp]"त्यसो भए scroll अनन्त लामो बनाउन मिल्छ?"[/] उसोपले सोध्यो।

[robin]"मिल्दैन।"[/] रोबिनले भनिन्। [robin]"ओरेकलको टेबल एउटा निश्चित नापको छ। त्यसलाई context window भनिन्छ। input र output दुवै मिलेर त्यो टेबलमा अटाउनुपर्छ। नअटाए पुराना message काट्नुपर्छ, वा तिनको सारांश बनाउनुपर्छ।"[/]

@recall api-call | ओरेकलकहाँ जाने विधि फेरि एकपटक सुन।

अब ओरेकलको लालटिन हेर। त्यो लालटिन कहिले चिसो हुन्छ, कहिले तातो हुन्छ।

@read teach
model ले हरेक पाइलामा अर्को token को सम्भावना निकाल्छ, र त्यहाँबाट एउटा token छान्छ। temperature ले त्यो छनोटको आकार बदल्छ। temperature ले logits लाई भाग गर्छ, अनि softmax लाग्छ। temperature कम भयो भने सबैभन्दा सम्भावित token लगभग सधैं छानिन्छ, र उत्तर स्थिर हुन्छ। temperature बढी भयो भने कम सम्भावित token पनि छानिन्छ, र उत्तर फरक फरक आउँछ।

[sanji]"top_p चाहिँ के हो?"[/] सान्जीले चुरोट निभाउँदै सोध्यो।

[nami]"top_p भनेको टोकरी हो।"[/] नामीले भनिन्। [nami]"सबैभन्दा सम्भावित token बाट सुरु गर्छौ, र तिनका सम्भावना जोड्दै जान्छौ। जोड p पुगेपछि टोकरी बन्द हुन्छ। त्यसपछि त्यही सानो टोकरीभित्रबाट मात्र token छानिन्छ। top_k चाहिँ अझ सजिलो छ, किनभने त्यसले सबैभन्दा सम्भावित k वटा token मात्र राख्छ।"[/]

@read hush
evaluation मा उत्तर दोहोर्याउन मिल्नुपर्छ, त्यसैले त्यहाँ प्रायः temperature शून्यको नजिक राखिन्छ। तर pass@k जस्तो नाप लिँदा धेरै फरक नमुना चाहिन्छ, र त्यहाँ temperature बढाइन्छ। यो कुरा आठौं टापुमा फेरि आउँछ।

लुफीले scroll समात्यो, र ढोकाबाट पस्यो। यसपटक ओरेकलले पूरै scroll पढिन्, र भनिन् कि लुफीलाई मासु मन पर्छ। लुफी खुसीले हाँस्यो।

@recall api-call | टापु छाड्नुअघि विधि अन्तिम पटक, बिस्तारै सुन।

@tier medium

रोबिनले केही थप कुरा सुनाइन्। [robin]"ओरेकलको उत्तर पर्खिरहन पर्दैन।"[/] उनले भनिन्। [robin]"streaming मा उत्तर token token गरेर आउँछ, र प्रयोगकर्ताले पहिलो शब्द चाँडै देख्छ। त्यसलाई time to first token भनिन्छ, र latency नाप्दा यो छुट्टै गनिन्छ।"[/]

[franky]"एउटै लामो system prompt हरेक पटक पठाउँदा महँगो हुँदैन?"[/] फ्र्याङ्कीले सोध्यो।

[robin]"हुन्छ, त्यसैले prompt caching छ।"[/] रोबिनले भनिन्। [robin]"scroll को सुरुको भाग हरेक पटक उस्तै छ भने server ले त्यो भाग सम्झेर राख्छ। दोस्रो पटकदेखि त्यो भाग सस्तो र छिटो पढिन्छ। त्यसैले नबदलिने कुरा सधैं सुरुमा राख, र बदलिने कुरा पछाडि राख।"[/]

@read teach
अर्को कुरा stop sequence हो। कुनै निश्चित शब्द आएपछि model रोकियोस् भन्ने चाहियो भने stop sequence दिइन्छ। त्यसबेला stop_reason मा stop_sequence आउँछ। agent बनाउँदा चौथो किसिमको stop_reason पनि आउँछ, र त्यो tool_use हो। त्यसको कथा तेस्रो टापुमा छ।

@tier long

नामीले अन्तर्वार्ताको एउटा प्रश्न सम्झिन्। [nami]"कसैले सोध्छ कि उही prompt मा temperature शून्य राख्दा पनि उत्तर किन फरक आयो।"[/] उनले भनिन्। [nami]"उत्तर यो हो कि server मा batch र floating point को क्रम बदलिन सक्छ, त्यसैले शून्य temperature पनि पूर्ण रूपमा निश्चित हुँदैन। त्यसैले evaluation मा एउटै प्रश्न धेरै पटक चलाएर हेर्नु राम्रो हुन्छ।"[/]

[chopper]"अनि context window भरियो भने के गर्छौ?"[/] चोपरले सोध्यो।

[nami]"तीन बाटा छन्।"[/] नामीले भनिन्। [nami]"पुराना turn काट्न सकिन्छ। पुराना turn को सारांश बनाएर एउटै छोटो message मा राख्न सकिन्छ। वा सबै कुरा बाहिर कतै राखेर चाहिएको टुक्रा मात्र खोजेर ल्याउन सकिन्छ। त्यो तेस्रो बाटो पाँचौं टापुमा पुगेपछि बुझिन्छ।"[/]
