# ७ — मर्मतको डक: SWE-agent, Agentless, Sandbox र Program Repair

सातौं टापुमा जहाज मर्मत गर्ने एउटा ठूलो डक छ। यहाँ संसारभरिका टुटेका जहाज आउँछन्। डकको भित्तामा एउटा लामो सूची टाँसिएको छ, र त्यसमा हरेक जहाजको समस्या लेखिएको छ।

फ्र्याङ्कीले सूची पढ्यो। [franky]"यी issue हुन्!"[/] उसले भन्यो। [franky]"हरेक issue मा कसैले लेखेको छ कि जहाज कहाँ चुहिन्छ। तर कुन फलक भाँचिएको छ भनेर लेखेको छैन।"[/]

@read teach
coding agent को काम ठ्याक्कै यही हो। उसलाई एउटा repository दिइन्छ, र एउटा issue दिइन्छ। उसले कुन फाइलमा गल्ती छ भनेर खोज्नुपर्छ, सुधार लेख्नुपर्छ, र सुधार काम गर्छ कि गर्दैन भनेर जाँच्नुपर्छ। अन्त्यमा उसले एउटा patch बुझाउँछ।

डकमा दुई किसिमका कालीगढ थिए। पहिलो कालीगढ जहाजभित्र पस्थ्यो, आफूखुसी यता उता हेर्थ्यो, फलक खोल्थ्यो, र मन लागेको ठाउँमा हथौडा चलाउँथ्यो। ऊ स्वतन्त्र agent थियो।

@read teach
त्यो पहिलो कालीगढ SWE-agent जस्तो हो। SWE-agent ले agent loop भित्र shell र फाइल सम्पादक प्रयोग गर्छ। तर त्यसको मुख्य सिकाइ agent computer interface हो। सम्पादकले एक पटकमा सय line जति मात्र देखाउँछ, खोज्ने command ले छोटो नतिजा दिन्छ, र edit गर्दा syntax बिग्रियो भने linter ले त्यो edit तुरुन्तै अस्वीकार गर्छ। model का लागि बनाइएको सरल interface ले नतिजा धेरै सुधार्छ।

दोस्रो कालीगढ चाहिँ शान्त थियो। उसले आफूखुसी घुम्दैनथ्यो। उसले सधैं एउटै तीन चरण पछ्याउँथ्यो, र उसलाई सबैले Agentless भन्थे।

@algo agentless
Agentless को विधि तीन चरणको छ, र क्रम localize, repair र validate हो। localize चरणमा पहिले repository को फाइल संरचना र issue पढेर शङ्कास्पद फाइल छान, त्यसपछि ती फाइलभित्रका class र function छान, अनि सम्पादन गर्नुपर्ने ठ्याक्कै line हरू छान। repair चरणमा ती ठाउँका लागि धेरै वटा उम्मेदवार patch बनाऊ, र हरेक patch लाई search and replace diff को रूपमा लेख। validate चरणमा पहिले issue लाई दोहोर्याउने reproduction test बनाऊ, त्यसपछि हरेक patch मा त्यो test र पुरानै regression test चलाऊ। test फेल गराउने patch हटाऊ, बाँकीलाई normalize गरेर बहुमतले छान, र एउटा मात्र patch बुझाऊ।
@end

[usopp]"agent नै नभई कसरी राम्रो काम हुन्छ?"[/] उसोपले सोध्यो।

[robin]"किनभने हरेक चरण सानो र नाप्न मिल्ने छ।"[/] रोबिनले भनिन्। [robin]"localize ठूलो जंगलबाट सानो ठाउँ छान्छ। त्यसपछि repair लाई धेरै पढ्नु पर्दैन। validate ले कमजोर patch फाल्छ। स्वतन्त्र agent ले कहिलेकाहीँ बाटो बिराउँछ, तर यो निश्चित pipeline सस्तो छ, र दोहोर्याउन मिल्छ।"[/]

@read teach
localize चरण किन यति महत्त्वपूर्ण छ भने गलत फाइल छानियो भने अरू सबै चरण बेकार हुन्छन्। त्यसैले localize लाई तहतह गरेर गरिन्छ। पहिले फाइल, अनि function, अनि line छानिन्छ। धेरै प्रणालीले यहाँ embedding खोज पनि सँगै चलाउँछन्, र दुवै सूची मिलाउँछन्।

@recall agentless | शान्त कालीगढको विधि फेरि एकपटक सुन।

फ्र्याङ्कीले जहाजलाई सिधै समुद्रमा परीक्षण गरेन। उसले पहिले जहाजलाई एउटा बन्द पोखरीमा राख्यो, र पानी भर्यो। [franky]"यहाँ डुब्यो भने केही बिग्रँदैन।"[/] उसले भन्यो।

@read teach
त्यो पोखरी sandbox हो। coding agent ले चलाउने code र test सधैं अलग्गै container भित्र चलाइन्छ, प्रायः Docker मा। त्यहाँ network बन्द हुन्छ वा सीमित हुन्छ, CPU र memory को सीमा हुन्छ, र हरेक command को timeout हुन्छ। agent ले गल्तीले फाइल मेटायो भने पनि बाहिरको संसार सुरक्षित रहन्छ। अनि हरेक काम सफा container बाट सुरु हुन्छ, त्यसैले नतिजा दोहोर्याउन मिल्छ।

[chopper]"test पास भयो भने patch पक्का सही हुन्छ?"[/] चोपरले सोध्यो।

[robin]"पक्का हुँदैन।"[/] रोबिनले भनिन्। [robin]"यसलाई patch overfitting भनिन्छ। test कमजोर छन् भने गलत patch पनि पास हुन्छ। कहिलेकाहीँ patch ले test लाई नै बदलेर पास गराउँछ। त्यसैले मूल्याङ्कन गर्दा agent ले नदेखेका लुकेका test चलाइन्छ, र test फाइल बदल्ने patch लाई शङ्काले हेरिन्छ।"[/]

@read hush
program repair को पुरानो विचार generate and validate हो। धेरै सुधार बनाऊ, र test ले छान। LLM आएपछि सुधार बनाउने भाग धेरै बलियो भयो, तर छान्ने भाग अझै test मै भर पर्छ।

डकको सूचीमा अर्को issue आयो। शान्त कालीगढले फेरि उही तीन चरण सुरु गर्यो।

@recall agentless | डक छाड्नुअघि Agentless को विधि अन्तिम पटक सुन।

@tier medium

नामीले मूल्याङ्कनको कुरा सम्झाइन्। [nami]"coding agent लाई SWE-bench ले नाप्छ।"[/] उनले भनिन्। [nami]"त्यहाँ हरेक काम एउटा वास्तविक GitHub issue हो। patch लगाएपछि दुई किसिमका test चलाइन्छन्। fail to pass test पहिले फेल हुन्थे, र अब पास हुनुपर्छ। pass to pass test पहिले पनि पास थिए, र अझै पास हुनुपर्छ। दुवै समूह पास भए मात्र काम resolved मानिन्छ।"[/]

@read teach
coding agent का अरू औजार पनि छन्। repository map ले फाइल र function को छोटो नक्सा दिन्छ, ताकि model ले पूरै code नपढी बाटो चिनोस्। edit गर्ने ढाँचा पनि महत्त्वपूर्ण छ। पूरै फाइल फेरि लेख्नुभन्दा search and replace block वा unified diff सस्तो पर्छ, र गल्ती कम हुन्छ।

@tier long

फ्र्याङ्कीले एउटा पुरानो कुरा सुनायो। [franky]"धेरै उम्मेदवार बनाउँदा temperature बढाइन्छ।"[/] उसले भन्यो। [franky]"फरक फरक patch आउँछन्, र तीमध्ये कम्तीमा एउटा सही हुने सम्भावना बढ्छ। त्यसपछि test र बहुमतले छान्छौ। यो नै आठौं टापुको pass at k सँग जोडिन्छ।"[/]

[zoro]"agent ले खतरनाक command चलायो भने?"[/] जोरोले सोध्यो।

[robin]"त्यसैले sandbox भित्र पनि अनुमति सीमित राखिन्छ।"[/] रोबिनले भनिन्। [robin]"command को allowlist राख, गोप्य key कहिल्यै container भित्र नराख, र हरेक command trace मा लेख। सुरक्षा पनि एउटा मूल्याङ्कन हो, र त्यो तेह्रौं टापुमा आउँछ।"[/]
